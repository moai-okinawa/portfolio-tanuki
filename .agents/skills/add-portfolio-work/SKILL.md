# ポートフォリオに作品を追加

このスキルの実行依頼には作品1件の追加、コミット、push、自動公開が含まれる。スキル自体の作成・編集依頼では作品追加を実行しない。

## 情報を確認する

編集前にユーザーに「作品名・説明・公開URL」をまとめて質問し、回答を待つ。提示済みの項目は復唱し、不足分だけ聞く。勝手に補わない。
URLはHTTP/HTTPSに限定し、秘密情報を含むURLや不明な値は確認する。

## 既存の形で1件追加する

1. ルートの `AGENTS.md`、`DESIGN.md`、`git status` と差分を読む。見た目はDESIGN.mdに従う。
2. `tanuki/dist/index.html` の `#works .work-grid`、`projects` 配列、`[data-work]` のイベント処理、`#work-dialog` と、`tanuki/dist/cute.css` を読む。現在の実装に合わせ、添字や件数を決め打ちしない。
3. 最後に作品カードを1件追加する。既存の `.work` ボタン、`.art` プレビュー、`.work-meta` の作品名と矢印、`.work-caption` の階層・余白・角丸・ホバーを揃える。対応する制作メモのデータを追加し、`data-work` と配列の添字を一致させる。
4. 説明を制作メモに表示する。URL表示がまだなければ、データの `url` と、ダイアログ内の「作品を見る ↗」リンクを最小限追加する。`.pill` を再利用し、URLのない既存作品では非表示にする。開くたびにリンク先・表示状態を更新し、前の作品のURLを残さない。ボタンにリンクを入れ子にしない。別タブなら `rel="noopener noreferrer"` を使う。
5. 文字列はHTML用にエスケープし、JavaScriptデータは安全にJSON化する。表示には `textContent` を使い、ユーザー入力を `innerHTML` に渡さない。
6. 画像未提供なら、既存のCSSで紙の見本と作品名を使った装飾プレビューを作る。実サイトのスクリーンショットと偽らない。担当範囲・技術・年は創作しない。タグは省略でき、キャプションは「制作物」など中立な表記にする。
7. 提供された作品にSAMPLE表記を付けない。既存サンプルは残し、「全作品がダミー」と読める注記があれば今回の作品と区別する文言に調整する。他の作品・ブログ・アニメーション・公開設定は保持する。

## 検証する

- `git diff --check`、相対リンク・画像・CSSの参照確認、カードとデータが1件ずつ増えたことの確認を行う。
- 既存サーバーを再利用するか、ルートから `python3 -m http.server 4173 --bind 127.0.0.1 --directory tanuki/dist` を実行する。
- ブラウザで通常幅・スマートフォン幅の表示、新旧カードの制作メモ、URLの表示・非表示、閉じる操作とフォーカスを確認する。ブラウザが使えない場合は静的確認と未確認点を区別して報告する。

## コミット・push・公開確認

- remoteとブランチを確認する。通常は `moai-okinawa/portfolio-tanuki` の `main`。ユーザーの別指定がなく送信先が違えば確認する。
- 今回の変更だけをステージする。同じファイルの無関係な変更も含めない。コミット例は `Add portfolio work: <作品名>`。ユーザー入力をシェルコードへ直接展開しない。
- 通常のpushを行い、force pushはしない。利用可能なGit認証を使い、一時CLIの固定パスを前提にしない。認証情報をログに出さない。
- 認証・権限エラーは原因を確認し、同じ失敗を繰り返さない。ユーザーの認証が必要ならコミットを保持して必要な操作を案内し、回答を待つ。未承認の権限拡大で回避しない。pushの成否が不明ならリモートのコミットを照合する。
- `.github/workflows/deploy-pages.yml` が起動した今回のコミットの実行を確認する。失敗時はログを調べ、今回の変更に起因する問題を直す。外部の権限・サービスが原因なら必要な対応を報告する。
- `https://moai-okinawa.github.io/portfolio-tanuki/` に作品名・説明・URLが反映されたか確認する。pushだけで公開成功とはしない。
- 最後に作品名・コミット・公開URL・確認結果を簡潔に伝える。未完了なら止まった段階を明記する。
